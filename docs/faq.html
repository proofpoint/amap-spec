FAQ

Frequently asked questions

Is AMAP a new mail protocol?

No. AMAP is not a mail transport, not agent-to-agent RPC, and not a policy language. It specifies the seam between an agent's connector and a trusted runtime that does the mailing. Between organisations there is only ordinary email, over standard protocols.

Does my counterparty need AMAP?

No. AMAP adds nothing to the wire, so a counterparty needs nothing but an email address. It can be a person with an inbox, a person with an assistant, or its own agent, with AMAP or without. One side can start today, and the other side changes nothing.

Does AMAP stop prompt injection or business email compromise?

No, and it doesn't claim to. It assumes the agent will sometimes be fooled and limits what a fooled agent can do by email. A trusted runtime can hold a pretext back before the agent sees it. If one gets through, the agent can only ask to reply, and the runtime decides. AMAP governs the email channel only. The agent's other tools need their own safeguards.

Can't a bad actor sign messages too?

Yes, just as with DKIM. A signature is a verifiable identifier to hang reputation on, not proof of legitimacy. Today AMAP's signed statements run only between configured peer runtimes. Extending verification to any recipient, and building reputation on it, is whitespace. See Identity.

What does the agent actually see?

Only what the runtime delivers into its inbound/ tree. Each delivered message carries runtime-asserted labels, such as sender standing and attachment dispositions. A message the runtime quarantines produces no notice at all (§ Inbound). Attachment bytes are published only for attachments the runtime marks clean, and that label is the runtime's assertion, not a scanner verdict.

Can the agent choose who it emails?

It can name anyone, since every request names its recipients. It can't decide who actually receives anything. The runtime evaluates recipient policy over exactly the recipients it will transmit to, and it never adds or substitutes one (§ Submit Request).

What happens on a policy miss?

The request results in queued_for_human. It is never silently sent and never silently dropped (§ Result). A recipient that policy permits is accepted without a human, so a person is involved only for the exceptions.

What if the runtime is compromised?

Then the trust boundary has moved. The runtime is the one trusted party by design, so that's where hardening belongs, and it's a much smaller, more auditable target than a model. AMAP's invariant is that no security property depends on the agent or connector behaving.

Why a filesystem, not an API?

Because a file drop carries no capability. The agent's only outbound act is to write an inert request into a runtime-owned namespace. There is nothing for it to call and no credential to misuse. The runtime reads the request, validates it, applies policy and writes exactly one result.

How does AMAP relate to MCP and A2A?

They sit at different layers. In the Claude Code connector, the agent sees ordinary MCP tools, and AMAP is the specification behind them. A2A connects agent services directly. See MCP, A2A and AMAP.

Can I use AMAP with my agent platform?

Yes, if a connector exists for it or you write one. The Claude Code connector is public. A connector needs no credentials, and the fixtures let you prove conformance without the other side present.

Is AMAP an IETF standard?

No. The AMAP Internet-Draft is ready for submission to the IETF, but it has not been submitted. The specification is v3.1.0 DRAFT. See Status.

Who controls AMAP, and is it free to use?

The AMAP specification, schemas, fixtures and reference implementations are published under the Apache License 2.0. Proofpoint originated AMAP, and it is open to every implementer. No one needs a particular vendor's runtime to conform or to interoperate. Changes land in the public specification first. See Get involved.
